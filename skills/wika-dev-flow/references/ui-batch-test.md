# 设备端批量操作与页面就绪检测

用于已确认导航路径的连续界面测试：一次下发计划，在设备本地执行触控、页面识别与抓屏，结束后统一取回结果。首次探索、按钮位置或布局变化时先单步确认，再形成批量计划。

## 已验证的脚本与适用范围

- 执行器：[scripts/ui_batch_probe.py](../scripts/ui_batch_probe.py)，已实机验证，支持基础切页计划和带控件 `guard` 的索引计划。设备端仅用 Python 标准库。
- 实测计划：[TZ956E V1.01 示例](../assets/tz956e-v101-ui-plan.json)。从已登录的主界面开始，执行“主界面 → 主菜单 → 版本页 → 主菜单 → 主界面”，每步保存一张截图。示例不包含登录凭据或自动登录操作。
- 当前执行器验证环境：ICM7100、ARMv7 小端 32 位 ABI、Python 3.7，`/dev/fb0` 为 32 bpp 且 RGB 通道各 8 位，`/dev/input/event1` 为多点触摸 type B，MT X/Y 轴为 53/54。`fb_fix_screeninfo` 步长偏移和 `input_event` 编码按此 ABI 实现；其他型号、64 位设备或触摸节点变化需先适配并验证。
- 示例绑定 `ICM6901_TZ956E_V1.01_20261015` 的页面布局；程序 SHA256 为 `f9c1bd9a1fdba8f2344d85414c3fbd178aa77f25433b600c4daa1348a2605ffe`。其他版本/项目重新确认页面特征和点击位置。

## 准备计划

需要从源码自动生成坐标或多页导航计划时，先用 [wika-ui-index](../../wika-ui-index/SKILL.md)。已有经核对的计划可直接进入执行部分；以下步骤也用于首次探索和单步校准。

1. 按在线部署流程核对正在运行的可执行文件、版本与配套配置，取得当前画面。确认测试期间可操作的页面和按键。
2. 查询 framebuffer 的实际宽高、stride、x/y offset 和 RGB 通道偏移，按实际格式抓图；查看触摸设备名称和坐标轴范围，单次验证一个无业务副作用的导航键。
3. 点击和识别点都使用**原始 framebuffer 坐标**。本例原始图为 1280×800，逆时针旋转 90° 后预览为 800×1280，预览点 `(xv, yv)` 换算为 `(1279-yv, xv)`。触摸值再按驱动的轴范围缩放；其他旋转/镜像关系先验证后使用。
4. 对每个目标页采集至少两张不同时间的实机截图，选择稳定、能区分其他页面的特征点。避开时钟、动态数值、闪烁告警、视频和按压高亮；避免大量黑色背景点，以免黑屏误判。用保留的另一张截图及其他页面、黑屏检查匹配效果。
5. 计划明确 `start_state`，每一步给出 `click` 和预期 `target`，关联相应测试项。长流程分成可独立核对起止状态的小段；页面就绪代表识别区域已显示，业务读数、按键作用及 CAN 收发另按测试项核对。

计划使用 UTF-8 JSON。可从示例复制后修改，其主要字段为：

| 字段 | 含义 |
| --- | --- |
| `framebuffer_size` | 原始图宽高 `[width, height]` |
| `states.<名称>.points` | 稳定特征点，每项为 `[x, y, r, g, b]`；每个状态至少一个点 |
| `states.<名称>.tolerance` | RGB 每通道最大允许差值 |
| `start_state` | 第一次点击前必须匹配的页面 |
| `steps` | 顺序执行的 `{name, click: [x,y], target}`；`name` 用简单文件名，决定截图名称 |
| `threshold` / `stable_matches` | 匹配率阈值 / 连续匹配次数 |
| `poll_s` / `timeout_s` | 两次检测之间的休眠时间 / 每步就绪等待上限 |

本例每页使用 256 个稳定点，颜色容差 20、匹配率至少 97%、连续匹配 2 次、检测间隔 50 毫秒、单步上限 4 秒。每次 framebuffer 读取和识别也有开销，50 毫秒不是实际采样周期保证。以上为实测起点，按页面特征与设备性能调整，先检查正确页能通过、其他页与黑屏能被排除。

## 一次下发、设备本地执行

将执行器与计划放到设备的临时测试目录，例如 `/tmp/ui-test/`。原程序部署、登录和测试前置条件由现场流程完成。示例计划需要已经进入 TZ956E 主界面。

在设备端运行：

```bash
python3 /tmp/ui-test/ui_batch_probe.py /tmp/ui-test/plan.json adaptive
```

执行器自行处理各步，成功后立即继续，期间不需要逐步取图等待 AI 判断。`/tmp/ui-test/adaptive/` 内包含各步 PNG 和 `result.json`，进程退出码 0 且 `passed=true` 表示该段导航完成。每步记录 `touch_ms`、`ready_wait_ms`、`capture_ms`、`elapsed_ms` 和最终匹配率。

异常处理与完成标准：

- 起始页不匹配：保存 `unexpected-start.png`，不发送点击。
- 计划含控件 `guard` 时，每次点击前先检查该控件的稳定特征；不匹配保存 `guard-failed-NN.png`，停止后续点击。记录 `guard_score/guard_ms`；索引计划的 `plan_id` 原样写入结果，供实机证据回填。
- 目标页在上限内未连续匹配：保存 `failed-NN.png` 和失败结果，停止后续操作。先查看画面和原因，再决定是否修改计划或程序；页面识别失败不是自动判定业务程序有缺陷。
- 正常退出和捕获异常时，脚本释放触摸；外部强制结束可能绕过 `finally`，由监督任务补充释放触摸和恢复。
- 执行器只负责界面操作与证据，不管理部署、Qt 进程、服务或挂载。将它放入有整体超时的**设备本地监督任务**（如 `subprocess.run(..., timeout=70)`，按实际流程长度调整），使 SSH 断开后也能完成收尾。监督任务在 `finally` 停止临时 Qt 进程、解除本轮临时挂载，并按测试前状态恢复服务；若要求保留测试程序运行，则按该已授权状态收尾。
- 原程序/现场数据与测试配置隔离。临时替换 `/apps` 视图时，先核对原始挂载与服务，保存基线；收尾后确认恢复挂载、服务 MainPID/运行文件及持久文件哈希。数据库、EDS、logo 按既有部署约定处理。

结果统一取回后，对关键截图做目视核对，将对应 T 项的结果、读数和证据填入测试文档。当前脚本支持点击；滑动尚未纳入本次实测。

需要自动判定页面/业务数值、选择开发回归、生成测试记录或缩略图时，按 [测试用例与证据](test-evidence.md) 接入主机工具。保留设备原始 JSON/PNG，回传摘要和缩略图后再按需取原图；图像识别通过只满足对应导航项，不能自动填写 CAN 或业务项通过。

## 性能对比与实测证据

只有需要比较性能时，才在同一版本、路径、前置状态和截图策略下运行基线：

```bash
python3 /tmp/ui-test/ui_batch_probe.py /tmp/ui-test/plan.json fixed fixed
```

最后一个 `fixed` 将每步改为固定等待 2 秒，随后仍检查目标页，避免基线盲点。重跑前确认起始页；本示例执行完会回到主界面。

2026-10-16 在 ICM7100/TZ956E V1.01 实测，三轮共 12 次切页通过：

| 模式 | 四次切页及四张 PNG 本地保存 |
| --- | ---: |
| 固定等待，每步 2 秒 | 10.08562 秒 |
| 页面就绪检测，第 1 轮 | 3.62731 秒 |
| 页面就绪检测，第 2 轮 | 3.73276 秒 |

自动检测两轮平均 3.68004 秒，设备端耗时减少 63.5%。基线也采用设备端批量执行，所以该比例仅反映等待策略变化，未计入减少 AI/SSH 往返的收益；网络下发、图片回传和 AI 阅读时间另计。实际就绪等待 258–710 毫秒，触控按压约 120 毫秒，每张 PNG 编码与保存约 0.33–0.36 秒。

实机另验证了错误起始页零点击；离线回放验证了延迟帧、目标超时停止后续动作及黑屏排除。测试后原服务恢复，原程序、数据库、logo、CAN0 EDS/H/VAR 哈希一致。这些结果覆盖本例页面导航与截图，不代表其他项目、滑动或业务/CAN 测试已经通过。
