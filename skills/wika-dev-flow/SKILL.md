# WIKA 显示器程序开发流程（wika-dev-flow）

把一次需求开发从输入到交付按固定节奏走完，环环有门禁，产物可追溯。EDS 修改、编译、在线测试与打包分别复用对应技能，本技能只负责编排、文档与交付纪律。

## 流程总览

```
需求输入（密文先解密）
    └─ 首次确认工程配置；每轮只读预检查（工程/SDK/连接/设备）
    ↓
①需求文档（含修改计划）
    ↓
②测试文档（测试项清单）
    ↓
③修改程序并确定最终版本（EDS/PDO 变更调用 wika-eds-edit）
    ↓
④编译并冻结本轮候选产物（wika-build）──失败──→ 回③修复后重编
    ↓通过
⑤在线测试（依次执行）
    ├─ 部署与版本/EDS 核对（wika-displayer-online）
    ├─ 界面测试准备：索引与导航计划（wika-ui-index）
    ├─ 开发迭代：变更/关联项 + 冒烟；交付候选：完整需求测试集
    ├─ 执行并断言：界面批量操作与就绪检测；按需 CAN 调试（wika-can-debug）
    └─ 统一结果回填测试文档，保留原始证据，优先回传摘要/缩略图
    ↓同一候选的完整交付测试通过
⑥核对 BIN 与冻结产物，脚本打包交付（.app + 需求文档 + 测试文档）
    ↓
⑦总结（交付总结 + 沉淀工程记忆）
```

每个阶段完成才进下一阶段。④编译失败或⑤发现程序缺陷，回③修复后重走④⑤；⑤遇到网络、设备前置条件或页面识别配置问题，修正后重做⑤。全部测试项通过才可进入⑥。

工程发现、只读预检查、候选快照和交付一致性工具见 [工程配置与产物冻结](references/project-and-release.md)。自动断言、开发/交付回归、报告回填和缩略图见 [测试用例与证据](references/test-evidence.md)。使用工具前读对应参考；本流程沿用现有设备监督方式，不新增任务调度或断线恢复机制。

## 文档约定

- 文档目录：`<工程根>/docs/`（如 `/home/ubuntu/Displayer/LGMRT/SDC190H/docs/`），不存在则创建。
- 命名：`需求文档_<YYYYMMDD>_<slug>.md`、`测试文档_<YYYYMMDD>_<slug>.md`，slug 用短英文或拼音（如 `counter-drilldepth`）。同一需求的两份文档用相同日期和 slug。
- 一份需求对应一套文档，迭代开发新需求时新建一套，不往旧文档里续写。
- 读文档按文件类型自动调用对应技能，不要裸读解析：`.doc/.docx`→**docx**、`.pdf`→**pdf**、`.xlsx/.xls/.csv`→**xlsx**；按所选主机检查 Python 及必要依赖，不套用其他电脑的解释器路径。`.md`/纯文本直接读。亿赛通密文先按阶段 0 解密再读。

### 需求文档模板

```markdown
# 需求文档：<一句话标题>
- 日期 / 型号 / 提出人：
- 状态：草稿 | 已确认

## 1. 背景与目标
## 2. 需求条目
  REQ-001 ...（每条可验证，含验收标准）
## 3. 修改计划
  | 文件/模块 | 改动内容 | 对应需求 |
## 4. 影响面与风险（涉及的 CAN 报文/翻译字典/图标等）
## 5. 范围外（本次不做）
```

### 测试文档模板

```markdown
# 测试文档：<一句话标题>
- 日期 / 型号 / 测试程序版本：
- 关联需求文档：<文件名>

## 测试项
| 编号 | 对应需求 | 前置条件 | 操作步骤 | 预期结果 | 结果 | 备注/证据 |
| T-001 | REQ-001 | ... | ... | ... | 待测 | |

## 测试记录
（每轮在线测试追加：日期、程序版本、各测试项 通过/未通过、未通过现象）
## 结论
```

## 阶段说明

### 阶段 0：需求输入
- 首次使用工程时发现并确认 `wika-project.json`，之后复用。配置记录构建入口/SDK、产物、启用的 EDS 三件套、数据库策略、设备服务及触摸节点；多候选不自动择一。每轮按 [工程配置与产物冻结](references/project-and-release.md) 做只读预检查，在停止设备程序前解决连接或环境问题。
- 需求以文件形式给出时（尤其来自 `/media/sf_Share` 共享目录），先判断是否亿赛通密文：头 200 字节扫 Esafenet 标记（`head -c 200 文件 | xxd | grep -a Esafenet`），xlsx/docx 解析报 BadZipFile 也是典型征兆；注意解密后的文件 `file` 命令仍报 esafenet，不能作为判断依据。**是密文则先调用 `esafenet-share-decrypt` 技能解密**（首选 cp 到本地磁盘透明解密），明文校验（PK 头/正常文本、zip 完整性）通过后才继续后续阶段，不允许对着密文硬解析或跳过。
- **需求分析先调用 `brainstorming` 技能（superpowers 技能集）**：先分类需求规模（bounded/architectural），逐条澄清歧义，再复述对需求的理解（一句话级别）。交互模式下遵守其确认门——需求文档"已确认"后才动码；自主模式下无对话者，降级为自我推演：做出**合理假设并写入需求文档**（标注"假设"），不要停下来等。
- 需求涉及 CAN 协议时先查协议表（如 `/home/ubuntu/CAN_SDC190H_dump.txt`）与既有代码用法，确认字段含义再落文档——字段来源搞错是最常见返工原因。

### 阶段 1：需求文档
- 读代码文件前（各阶段同理）先查工程有没有 `.codegraph/` 索引：没有则先调用 **codegraph** 技能 `build` 建图；已有则 `status` 确认新鲜（有源码改动先 `update`）。用 `search/defs/refs/impact` 定位符号与影响面，再只读命中的少量文件，替代大范围盲 grep。
- 按模板写 `docs/需求文档_*.md`。需求条目编号 REQ-XXX，修改计划落到**具体文件**（先调研代码再填表，禁止拍脑袋写文件名）。
- 调研时优先利用工程记忆（记忆索引里有各型号的关键机制，如字典索引对齐、页面数据流、选配标志位）。

### 阶段 2：测试文档
- 按模板写 `docs/测试文档_*.md`，每个 REQ 至少一个 T 项，结果列初始为"待测"。
- 测试项写**操作步骤和预期结果**，达到"换了个人也能照着测"的程度；涉及界面状态切换（选配有效/无效）要各出一条。
- 可自动判断的 T 项同时维护 [结构化用例](references/test-evidence.md)，写明需求、源码/资源/协议依赖、输入与前置状态、期望值/帧、时间窗、验证层级和证据来源。无法自动测量的项保留人工验收，缺数据为未测，不能由页面识别成功代填业务通过。

### 阶段 3：修改程序
- 在本轮正式候选编译前确定最终版本串、日期及其源码位置；按工程实际入口修改，不限定为某个型号的 QML 文件。临时版本切回正式版本后仍须重新编译并验收。
- 动码前调用 **karpathy-guidelines** 技能，按其准则执行修改：只做需求相关的外科手术式改动（不顺带重构）、写前提早暴露假设、先定义可验证的成功标准。
- 严格按修改计划执行；计划与实际不符时（调研遗漏、发现更好的做法），先更新需求文档的修改计划再动码，保持文档与代码一致。
- 修改 EDS/PDO 时，调用独立技能 [wika-eds-edit](../wika-eds-edit/SKILL.md)，按其方法修改配置并核对 .h/.var 与源码引用。该技能包含已实测的现有 PDO COB-ID 修改方法，以及对象、映射或变量顺序变化时的处理边界。
- 遵守工程既有约定（词条进字典要保持中/英/西索引对齐、qrc 登记资源、内存释放惯例等——详见各型号记忆）。
- 程序修改后判断是否要更新 codegraph：用 **codegraph** 技能 `status` 查改动——动了被索引的源码（.cpp/.h/.qml/.js/.py 等）就 `update` 增量刷新，只改文档/资源可跳过；新增或重命名符号后必须 update，保证后续阶段查询准确。

### 阶段 4：编译（门禁）
- 调用 **wika-build** 技能做增量编译，记录 qmake/make 的真实退出码与完整日志；出现管道时保留构建命令本身的状态。门槛：所执行构建命令均退出 0、最终运行产物是匹配目标的 ARM ELF，且含预定版本串。错误关键字计数只作诊断。
- 编译出错 → 修复 → 重编，循环直到通过；这一步不过不允许进在线测试。
- 最终裁剪等处理完成后，按 [工程配置与产物冻结](references/project-and-release.md) 保存本轮程序与配套文件的候选快照及清单，绑定构建结果、源码、配置和 SHA256。构建直接输出 `BIN` 时也留存快照；后续源码、SDK/配置、产物变化须重新构建或核验并创建新候选，原验收记录不自动沿用。

### 阶段 5：在线测试（门禁）
- 执行顺序：部署与版本核对 → 界面索引及导航计划准备 → 逐项测试 → 回填证据与验收。
- 部署前以当前候选快照（与本轮 `BIN` 核对一致）为基准，核对程序实际加载位置的 `can0/can1.eds/.h/.var`（按工程启用通道）。匹配才可保留；缺失、切换工程或 CAN 配置变化时，备份后成套同步。数据库按保留/迁移/初始化需求单独处理，现场运行数据库不要求与默认数据库字节相同。
- 调用 **wika-displayer-online** 技能部署到设备，读取实际运行进程的可执行文件，核对程序及加载配置与本轮候选一致，保存核验记录。
- **界面测试准备**：对已适配的 Qt/QML 界面，调用 [wika-ui-index](../wika-ui-index/SKILL.md)，从本轮源码、资源和对应实机截图建立界面操作索引，将测试文档中的页面/控件映射为坐标并生成导航计划。先检查索引新鲜度；未变化可复用，源码、资源或校准条件变化时按该技能重建。保留未解析项的原因，首次探索或未适配布局先单步校准；适配边界见该技能。
- 按 [测试用例与证据](references/test-evidence.md) 选择开发回归或交付回归。开发轮运行变更项、关联项和基础冒烟；依赖不完整、未知变更或公共框架/协议变化时扩大到完整集。交付候选执行本次需求的全部 T 项；开发轮通过不允许进入阶段 6。
- 逐项执行所选 T 项，断言实际页面/数值/帧，记录通过/未通过/未测及截图/读数/日志。CodeGraph 影响分析结合 UI 索引、资源、EDS 和数据库变化确定范围，不能只用符号关系排除测试。
- 已确认导航路径的连续界面测试，优先使用 [设备端批量操作与页面就绪检测](references/ui-batch-test.md)：一次下发操作序列，每步识别到目标页后继续，异常停止并保存证据。该说明包含实测脚本、TZ956E 示例计划、坐标校准、执行与恢复方法；首次探索或页面布局变化时先单步确认。
- CAN 收发排查、本机脚本模拟或总线联调调用 [wika-can-debug](../wika-can-debug/SKILL.md)；EDS 改动同时按 [wika-eds-edit](../wika-eds-edit/SKILL.md) 核对对象与变量映射。按本次需求选择模拟或物理测试，将对应范围、结果及证据填入测试文档。
- 界面导航实测通过后，按 **wika-ui-index** 回填与本次计划、程序版本绑定的实机验证记录；源码/图片确认只用于准备，不能代替 T 项的实测结论。
- 测量值、断言、程序/候选标识和证据哈希统一写入本轮结果，再生成报告、回填测试文档；先回传摘要和缩略图，关键验收或失败项拉取原图。原始证据保留，回放结果单独标注；阶段耗时按实际测量记录，未测量项不估算。
- **同一候选的完整交付测试全部通过**：更新测试文档（结果列 + 测试记录 + 结论），进入打包。
- **任一未通过**：先记录失败项与原因。程序缺陷回阶段 3 修复，再走④⑤，开发轮先测影响范围，最终候选仍跑完整需求集；网络、设备前置条件或页面识别配置问题修正后重做⑤，不能仅凭导航识别失败修改业务代码。

### 阶段 6：打包交付
- 核对冻结候选、实际测试程序/配置和完整交付测试结果属于同一轮。版本号已在阶段 3 确定；这里直接使用通过验收的文件，发生重编或最终版本变化则回④⑤。
- 将通过测试的冻结可执行文件更新到 `BIN`；若已直接输出到 `BIN`，只需核对哈希。以同一候选的程序、EDS/.h/.var、默认数据库、logo 制包，逐文件比较载荷与清单，并用 [候选验证工具](references/project-and-release.md) 检查源码/配置漂移及交付验收标识。独立试验 ID 不自动写入正式配置；数据库迁移或升级启动方式变化另做对应安装/重启验收。
- 调用 **wika-app-package** 技能打包。build_app.py（自算 MD5）是实机验证过的可信首选路径；mgmt-tool 可能不写产物，不要死等。
- 交付清单（三项缺一不可，逐项确认存在并向用户报路径）：
  1. `.app` 安装包（工程根，命名 `LGMRT_<型号>_V<版本>_Build<日期>.app`）
  2. `docs/需求文档_*.md`
  3. `docs/测试文档_*.md`（结果列已全部填写）
- 用户要求发共享目录时拷到 `/media/sf_Share/<型号>/`，并提醒：共享目录文件会被亿赛通透明加密，主机侧保留明文。
- 交付保留候选清单、构建日志和本轮结果，保证版本、程序/配置指纹、测试项及包内文件可追溯。

### 阶段 7：总结（收尾）
- 向用户输出本次闭环总结（简短清单）：REQ 条目与实现状态、实际改动文件及与修改计划的差异、测试结论、交付物（.app 名/版本号）、范围外与遗留事项。
- 把本次新增的机制、踩过的坑、工程约定沉淀进工程记忆（新建或更新对应记忆文件 + 索引）——流程起点"优先利用工程记忆"正是靠这里回填。

## 从中间切入

用户经常不需要从零开始，按入口就近进入并补齐缺失文档：
- "只打包" → 阶段 6，核对冻结产物及本次授权的验收范围；缺少测试记录如实标注，不补写通过。
- "改完帮忙测" → 阶段 4 起，若无测试文档先按阶段 2 补一份。
- "按上次的文档继续" → 读 docs/ 里对应文档（若读到密文先按阶段 0 解密），从"状态"字段判断接续点。

## 红线

- 不允许测试文档"待测"状态下交付；结果列必须有值。
- 不允许跳过编译门禁直接上设备。
- 每轮测试（含回归）都要在测试文档留下记录，失败→修复→重测的轨迹可追溯。
- 交付时版本串、.app 包名、测试文档里的"测试程序版本"三者一致。
- 运行程序、冻结候选、BIN 和包内程序使用同一份最终文件；配置按启用通道核对。开发轮、历史回放或单层探针的通过不替代完整交付验收。
