# WIKA EDS 修改与实机收发验证

先确定修改的是现有 PDO 的 ID，还是对象字典、数据宽度、映射或变量顺序；两类改动的验证范围不同。按“确认协议与备份 → 修改并检查三件套 → 按需重编 → 部署与收发验收 → 恢复或交付”执行，保存差异与测试证据。实际设备连接和启停复用 wika-displayer-online，业务工程编译复用 wika-build；只修改文件时完成差异检查，并明确尚未进行实机验证。

## 已验证的方法与边界

2026-10-15 在 TZ956E 工程、真实 ICM7100、`/usr/lib/libhsm.so` 与 IXXAT USB-to-CAN V2 上，使用 CanSimTool 1.1.3 完成以下试验：250000 bit/s、扩展帧，只改现有 PDO 的 COB-ID，原对象字典和八字节映射不变。

| 修改位置 | 原值 | 试验值 |
| --- | --- | --- |
| `can0.eds` → `[1400sub1]` → `DefaultValue`，接收 PDO1 | `0x18FA10EF` | `0x18FFAAE5` |
| `can0.eds` → `[1800sub1]` → `DefaultValue`，发送 PDO1 | `0x1C080060` | `0x18FFABE5` |

SDK 加载成功，接收变量及对象正确更新，显示器按新发送 ID 回传；CAN 盒物理 RX 收到两组完整数据。旧接收 ID 的帧确实到达显示器原始 CAN socket，但没有更新新映射。

该结论适用于本次“现有 PDO 改 ID、原映射保持”的情形。新增/删除对象、改变信号位宽、重排变量、完整 J1939 协议及业务 Qt 页面的验收需要相应测试，不能由这次试验外推。表中的试验 ID 不是其他工程的默认协议。

## 修改前确认

1. 从当前工程 `BIN` 备份对应通道的 `.eds`、`.h`、`.var`，记录原哈希，区分独立试验副本与正式修改。
2. 从协议和调用代码确认通道、节点、波特率、接收/发送方向、帧类型、PDO 编号及变量含义；查明程序实际加载的 EDS 路径，不只看文件名。
3. 核对 EDS 的对象/映射、`.var` 的变量编号，以及 `.h` 的枚举和源码引用。本例接收变量 `0–7` 对应 `0x2000:1–8`，发送变量 `129–136` 对应 `0x206C:1–8`；其他工程重新查表。

## 只改现有 PDO 的 COB-ID

1. 在 EDS 中按 **section + key** 精确修改对应 `DefaultValue`，如上表的两处。每个目标先断言 section 和键唯一存在，保留文件原编码、换行及其他字段；输出差异确认只改计划内容。
2. 保持对象字典、映射宽度、映射条目和变量顺序。本例 `[1600sub*]`、`[1A00sub*]` 不变，`.var` 字节完全不变。
3. 检查 `.h` 中含旧 ID 的枚举名称/注释。若同步改名，一并更新业务源码引用，保持枚举数值与 `.var` 一致，再重新编译。不要为改一个 ID 重排变量编号。
4. 结合当前 SDK 确认 COB-ID 中帧标志/控制位的解释和扩展帧模式。本例是直接修改所列 ID，再调用 SDK 的扩展帧模式；不能把这一表示法未经核对套到其他 SDK。
5. 编译业务程序后按下文在线验收；独立 SDK 探针通过只证明所测配置/API 路径，业务程序仍按需求测试。

### 对象或映射变化

本工程原 `.eds/.h/.var` 标注由 mgmtTool 生成。若改动对象 index/subindex、数据类型/宽度、PDO 映射或变量顺序，先确认工程可用的编辑与导出入口，将三件套与源码引用同步调整，再检查变量编号和信号解码并重编测试。尚未核验的 mgmtTool 菜单、按钮或 CLI 参数应明确标注未知，不编造操作步骤；本参考未提供这类改动已经实测通过的保证。

## 部署配置一致性

- 在线部署前备份原程序与配置，逐文件比较当前 `BIN` 和实际加载目录（本例为 `/apps`）。核对工程启用的各通道；缺失或不匹配的三件套成套同步，匹配才保留。
- “同工程仅改界面”也先确认配置一致；切换工程时，旧 EDS 能被 SDK 加载不代表其报文/变量属于新程序。
- 数据库和 logo 分别按需求处理，避免将“保留现场数据”误用于另一工程的 CAN 配置。SDK 初始化、文件一致和物理通信分别判定，不能仅凭 `ERROR-PASSIVE` 推定 EDS 是唯一原因。
- 独立试验可使用临时目录加载修改副本，由同一测试监督流程负责超时停止与恢复原服务。记录恢复结果和原文件哈希；设备重启后重新确认实际进程与配置，不沿用旧的“正在测试”状态。

## 实机收发验收

让 CAN 盒作为另一节点即可进行物理收发试验，不要求真实 PLC/整车控制器。选择工具的实体硬件后端，确认当前测试总线、波特率及帧类型。

本例临时暂停界面程序，在显示器使用实际 `libhsm.so` 调用以下接口，四项均返回 `0`：

```c
canopen_baud_rate(0, 250000);
canopen_start(0, 0x10, "<测试目录>/can0.eds");
canopen_j1939_mode(0, 1);
canopen_start_node(0, 0x10);
```

参数和函数签名以目标 SDK 头文件及工程封装为准。该 SDK 的 `j1939_mode` 在此用于扩展帧模式，不表示完整 J1939 协议已验收。

按下列顺序保存证据：

| 步骤 | 操作与通过标准 |
| --- | --- |
| 初始化 | 记录加载文件完整路径/哈希及 baud/start/extended/start_node 返回值。 |
| 旧 ID 对照 | 发旧接收 ID `18FA10EF`、数据 `A1A2A3A4A5A6A7A8`；确认帧实际到达原始 CAN 接口，SDK 对象保持基线值。仅“没收到回传”不足以证明映射拒绝。 |
| 新 ID 接收 | 发 `18FFAAE5 / 1122334455667788`；分别读取 `canopen_read_var_int(0,0..7,...)` 和 `canopen_read_int(0,0x2000,1..8,...)`，均为 `[17,34,51,68,85,102,119,136]`。 |
| 显示器发送 | 将八字节写入变量 `129–136`，调用 `canopen_send_pdo(0,1)`，记录所有写入及发送返回值；CAN 盒的 **rx** 日志须出现扩展帧 `18FFABE5` 和相同八字节。 |
| 第二组 | 换 `DEADBEEF01234567`，SDK 变量/对象均为 `[222,173,190,239,1,35,69,103]`，CAN 盒再收到对应回传。 |
| 收尾 | 停止探针、恢复先前服务，核对运行状态以及原程序/EDS 哈希；正式改动按需求保留，临时试验恢复原配置。 |

CanSimTool 的 `tx` 行或发送 API 成功不足以证明显示器发出了报文。物理发送证明使用实体 CAN 盒的 `rx` 行，并核对方向、ID、帧类型、DLC 和全部数据；软件回环单独记录。

远程网络不稳定时，可让显示器本机完成“接收更新→SDK 写变量→send_pdo”的有时限探针循环，Windows 本地控制 CAN 盒。这样去掉逐帧远程往返对时序的影响；仍须保存实际 SDK 值和硬件 RX 证据，并在退出时恢复服务。

## 回写 BIN 与打包

正式业务变更测试通过后，将实际测试过的可执行文件更新到 `BIN`，核对其哈希与运行文件一致。若 Makefile 已直接输出 `BIN/<程序>`，无需重复复制；TZ956E 的目标就是 `../BIN/TZ956E`。

以匹配的程序、EDS/.h/.var、默认数据库、logo 及工程所需其他资源制包，按 `wika-app-package` 校验包结构与载荷内容。独立试验的配置和探针不自动替换业务交付物。

测试文档保存：EDS 差异、三件套哈希、加载路径、SDK 返回值/接收值、CAN 原始收发记录与恢复结果。区分“配置/SDK/物理收发通过”和“整套业务/整车验收通过”。
